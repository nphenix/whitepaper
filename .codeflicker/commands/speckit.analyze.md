## 用户输入

```text
$ARGUMENTS
```

在继续之前, 你**必须**考虑用户输入(如果不为空).

## 概述

用户在触发消息中 `/speckit.analyze` 后输入的文本**就是**分析描述. 假设你始终可以在本次对话中访问它, 即使下面字面上显示 `$ARGUMENTS`. 除非用户提供了空命令, 否则不要要求用户重复.

基于该功能的三个核心制品, 执行以下操作:

1. **加载制品文件**
   - 从 `specs/[feature]/spec.md` 加载功能规范
   - 从 `specs/[feature]/plan.md` 加载实施计划
   - 从 `specs/[feature]/tasks.md` 加载任务清单
   - 确认所有文件都已通过各自的验证

2. **一致性分析**
   - **spec.md vs plan.md**:
     - 检查计划是否覆盖了规范中的所有功能需求
     - 验证技术方案是否满足规范的要求
     - 识别规范中提及但计划中遗漏的项目
     - 识别计划中新增但规范中未提及的项目
   - **plan.md vs tasks.md**:
     - 检查任务清单是否完整覆盖了计划中的所有阶段
     - 验证任务的优先级和依赖关系是否与计划一致
     - 识别计划中提及但任务中遗漏的工作项
     - 识别任务中新增但计划中未提及的工作项
   - **spec.md vs tasks.md**:
     - 检查任务清单是否直接映射到规范中的功能需求
     - 验证任务的验收标准是否满足规范的成功标准
     - 识别规范中要求但任务中未体现的功能点
     - 识别任务中超出规范范围的工作项

3. **重复性检查**
   - 识别三个制品中重复的需求、任务或描述
   - 检查是否存在冗余的技术方案或实现方法
   - 标记可能造成混淆或资源浪费的重复项

4. **模糊性识别**
   - 识别规范、计划或任务中不明确的描述
   - 检查是否存在歧义或多种解释的可能性
   - 标记需要进一步澄清的模糊点

5. **规范不足检测**
   - 识别规范中缺失但实施必需的细节
   - 检查计划中假设但未在规范中明确的要求
   - 识别任务中需要但未在规范或计划中说明的约束

6. **章程一致性验证**
   - **章程权威**: 项目章程(`.specify/memory/constitution.md`)在此分析范围内是不可协商的. 章程冲突自动为严重问题, 需要调整规范、计划或任务——而不是稀释、重新解释或默默忽略原则. 如果原则本身需要更改, 那必须在 `/speckit.analyze` 之外的单独、明确的章程更新中进行.
   - 验证规范、计划、任务是否都符合章程原则
   - 识别任何违反章程的项目
   - 检查文件长度、目录结构、临时文件等约束是否被遵守

7. **生成分析报告**
   - 创建详细的分析报告，包含:
     - 发现的问题清单
     - 问题的严重程度分类
     - 问题的根本原因分析
     - 解决建议和优先级

8. **建议改进措施**
   - 为每个发现的问题提供具体的改进建议
   - 建议需要重新审查的制品
   - 提供协调不一致性的策略

9. **报告完成情况**
   - 包括分析报告的文件路径
   - 总结发现的主要问题
   - 提供下一步行动建议

## 通用指南

### 问题分类标准
- **严重问题**: 影响项目核心目标、违反章程原则或导致重大风险的问题
- **中等问题**: 影响部分功能实现、可能导致延期或增加成本的问题
- **低等问题**: 影响文档质量、可读性或一致性但不影响实施的问题

### 分析深度
- 深入分析每个制品的细节，不遗漏重要信息
- 考虑制品间的相互影响和依赖关系
- 从多个角度审视问题，包括技术、业务和管理层面
- 基于事实和证据进行判断，避免主观臆断

### 报告格式
- 使用清晰、结构化的方式呈现分析结果
- 为每个问题提供具体的示例和引用
- 提供可操作的改进建议
- 保持客观、中立的分析态度

### 持续改进
- 从每次分析中学习，改进分析方法
- 总结常见的不一致模式
- 为未来的项目提供预防建议
- 建立分析结果的跟踪机制

## 附加要求

### 跨制品追踪
- 建立需求追踪矩阵，确保从规范到任务的完整映射
- 追踪每个功能需求在计划和任务中的实现
- 识别任何断开的链接或遗漏的环节

### 风险评估
- 评估每个不一致项对项目成功的潜在影响
- 考虑技术风险、进度风险和成本风险
- 为高风险项目提供缓解策略建议

### 利益相关者沟通
- 识别需要了解分析结果的关键利益相关者
- 准备适合不同受众的报告版本
- 建立问题反馈和讨论机制
- 确保改进措施得到适当的沟通和理解

### 质量门禁
- 定义分析通过的标准
- 建立问题解决的验证机制
- 确保所有严重问题在实施前得到解决
- 跟踪问题解决的进度和效果

### 知识管理
- 记录分析过程中发现的最佳实践
- 总结常见的陷阱和错误模式
- 建立可复用的分析模板和检查清单
- 为团队积累分析经验

## 分析流程

### 阶段 1: 制品收集和准备
1. 收集所有三个核心制品
2. 验证制品的完整性和版本
3. 准备分析工具和模板
4. 建立分析基准

### 阶段 2: 逐项对比分析
1. 执行 spec.md vs plan.md 的对比
2. 执行 plan.md vs tasks.md 的对比
3. 执行 spec.md vs tasks.md 的对比
4. 记录所有发现的不一致项

### 阶段 3: 深度分析
1. 对发现的问题进行分类和优先级排序
2. 分析问题的根本原因
3. 评估问题的潜在影响
4. 检查与章程的一致性

### 阶段 4: 报告编写
1. 汇总分析结果
2. 编写详细的问题清单
3. 提供改进建议
4. 准备执行摘要

### 阶段 5: 结果沟通和跟踪
1. 与相关团队分享分析结果
2. 讨论和确认改进措施
3. 建立问题解决的跟踪机制
4. 定期检查改进措施的执行情况

## 注意事项

- **保持客观**: 在分析过程中保持中立和客观的态度
- **全面覆盖**: 确保分析覆盖所有重要的方面和细节
- **证据充分**: 基于具体的证据和事实进行判断
- **沟通清晰**: 清晰地表达分析结果和建议
- **持续跟踪**: 建立机制跟踪问题的解决情况

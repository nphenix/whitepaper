## 概述

用户在触发消息中 `/speckit.clarify` 后输入的文本**就是**澄清描述. 假设你始终可以在本次对话中访问它, 即使下面字面上显示 `$ARGUMENTS`. 除非用户提供了空命令, 否则不要要求用户重复.

基于该功能规范, 执行以下操作:

1. **加载功能规范**
   - 从 `specs/[feature]/spec.md` 加载功能规范
   - 识别需要澄清的模糊点和不明确的地方

2. **分析模糊点**
   - 识别规范中的歧义、遗漏或不清楚的部分
   - 分析每个模糊点对功能实现的影响
   - 确定需要用户澄清的关键问题

3. **生成澄清问题**
   - 为每个模糊点生成具体、清晰的问题
   - 问题应该引导用户提供明确的答案
   - 提供可能的选项或示例以帮助用户理解
   - 按重要性和影响程度对问题进行排序

4. **处理用户反馈**
   - 接收用户对澄清问题的回答
   - 将用户的回答整合到功能规范中
   - 更新模糊点，使其更加明确和完整

5. **验证澄清结果**
   - 检查所有模糊点是否都得到了澄清
   - 确认更新后的规范是否清晰、完整
   - 验证规范是否仍然符合原始需求

6. **生成澄清报告**
   - 记录所有澄清的问题和答案
   - 总结规范的变更内容
   - 评估澄清对项目的影响

7. **报告完成情况**
   - 包括更新后的规范文件路径
   - 总结澄清的主要内容
   - 列出下一阶段（`/speckit.plan`）的准备就绪状态

## 通用指南

### 澄清问题设计原则
- **具体性**: 问题应该针对具体的模糊点，避免过于宽泛
- **清晰性**: 问题的表述应该清晰易懂，避免使用专业术语
- **引导性**: 问题应该引导用户提供有用的答案
- **完整性**: 确保涵盖所有关键的模糊点

### 问题类型
- **定义澄清**: 明确术语、概念或需求的定义
- **范围澄清**: 明确功能的边界和适用范围
- **行为澄清**: 明确系统在特定情况下的行为
- **优先级澄清**: 明确不同需求的优先级和重要性
- **约束澄清**: 明确技术、时间或资源约束

### 澄清过程管理
- **记录**: 详细记录每个问题和答案
- **跟踪**: 跟踪澄清过程的进展
- **验证**: 验证澄清后的规范是否满足需求
- **沟通**: 保持与用户的良好沟通，确保理解一致

## 附加要求

### 模糊点识别
- 系统性地检查规范的每个部分
- 识别可能引起误解的表述
- 考虑不同利益相关者的视角
- 关注关键功能和复杂逻辑

### 问题优先级
- 根据对功能实现的影响程度确定优先级
- 优先澄清关键路径上的模糊点
- 考虑时间和资源约束
- 平衡完整性和效率

### 答案整合
- 将用户的回答准确地整合到规范中
- 确保更新后的表述与整体规范一致
- 验证答案的合理性和可行性
- 记录变更的原因和依据

### 质量保证
- 确保澄清后的规范仍然符合原始目标
- 验证规范的完整性和一致性
- 检查是否存在新的模糊点
- 确认规范的可执行性

### 文档管理
- 维护规范的版本历史
- 记录所有的澄清和变更
- 保持文档的清晰和可读性
- 确保所有利益相关者都能访问最新版本

## 澄清工作流程

### 阶段 1: 规范审查
1. 仔细阅读功能规范
2. 识别潜在的模糊点
3. 记录模糊点的位置和内容
4. 评估每个模糊点的影响程度

### 阶段 2: 问题生成
1. 为每个模糊点生成具体问题
2. 设计问题的表述方式
3. 提供选项或示例（如适用）
4. 按优先级排序问题

### 阶段 3: 用户交互
1. 向用户提出澄清问题
2. 接收和记录用户的回答
3. 澄清用户的回答（如有必要）
4. 确认理解是否正确

### 阶段 4: 规范更新
1. 将用户的回答整合到规范中
2. 更新模糊点的表述
3. 检查更新后的规范是否一致
4. 验证规范的完整性

### 阶段 5: 验证和报告
1. 检查所有模糊点是否已澄清
2. 验证规范的质量
3. 生成澄清报告
4. 准备下一阶段的工作

## 注意事项

- **保持客观**: 在澄清过程中保持中立和客观的态度
- **尊重用户**: 理解用户的需求和限制
- **及时沟通**: 及时与用户沟通，避免误解积累
- **记录完整**: 详细记录所有的澄清过程和结果
- **持续改进**: 从每次澄清中学习，改进未来的工作方法

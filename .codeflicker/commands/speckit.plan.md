## 用户输入

```text
$ARGUMENTS
```

在继续之前, 你**必须**考虑用户输入(如果不为空).

## 概述

用户在触发消息中 `/speckit.plan` 后输入的文本**就是**计划描述. 假设你始终可以在本次对话中访问它, 即使下面字面上显示 `$ARGUMENTS`. 除非用户提供了空命令, 否则不要要求用户重复.

基于该功能规范, 执行以下操作:

1. **加载功能规范**
   - 从 `specs/[feature]/spec.md` 加载功能规范
   - 确认规范已通过质量验证

2. **分析技术背景**
   - 识别项目的技术栈和依赖项
   - 检查现有代码库的架构和模式
   - 识别需要扩展或修改的现有组件
   - 记录技术风险和约束

3. **定义项目结构**
   - 根据功能需求扩展项目目录结构
   - 识别需要创建的新目录和文件
   - 定义模块间的依赖关系
   - 确保结构符合设计原则（如分层架构、模块化）

4. **创建实施计划**
   - 将功能分解为具体的实施阶段
   - 为每个阶段定义清晰的目标和里程碑
   - 识别阶段间的依赖关系
   - 评估每个阶段的复杂度和风险
   - 确定并行或串行执行的任务

5. **生成数据模型**
   - 定义所有必要的数据实体和关系
   - 创建数据库 schema（如适用）
   - 定义 API 接口和数据流
   - 确保模型满足所有功能需求
   - 考虑性能和扩展性要求

6. **创建快速开始指南**
   - 提供环境设置说明
   - 包含必要的配置步骤
   - 提供示例代码和用法说明
   - 包含验证功能是否正常工作的步骤

7. **生成实施计划文件**
   - 使用模板结构将计划写入 `specs/[feature]/plan.md`
   - 用从功能规范派生的具体细节替换占位符
   - 保持章节顺序和标题
   - 包含技术决策的理由

8. **验证计划完整性**
   - 检查计划是否涵盖规范中的所有需求
   - 验证技术方案的可行性
   - 确认资源和时间估算合理
   - 识别潜在风险并提供缓解策略

9. **报告完成情况**
   - 包括计划文件路径
   - 总结主要技术决策
   - 列出下一阶段（`/speckit.tasks`）的准备就绪状态

## 通用指南

### 技术背景分析
- 详细说明技术栈选择的理由
- 识别与现有系统的集成点
- 记录任何技术债务或遗留问题
- 考虑性能、安全和可扩展性要求

### 项目结构设计
- 遵循现有的代码组织模式
- 确保新结构与现有架构兼容
- 考虑未来的扩展需求
- 定义清晰的模块边界和接口

### 实施阶段划分
- 每个阶段应该有明确的目标和可交付成果
- 考虑任务的依赖关系和优先级
- 识别可以并行执行的任务
- 为复杂任务分配足够的时间

### 数据模型设计
- 使用 UML 图或类似工具可视化数据关系
- 定义清晰的数据验证规则
- 考虑数据一致性和完整性约束
- 设计可扩展的数据结构

### 质量保证
- 在计划中包含代码审查流程
- 定义测试策略（单元测试、集成测试、端到端测试）
- 包含性能基准和监控要求
- 考虑安全审计和合规性检查

**注意**: 计划应该足够详细以指导实施, 但也要保持灵活性以适应实施过程中的变化.

## 附加要求

### 依赖管理
- 明确标识新功能所需的外部依赖
- 评估依赖的兼容性和维护状态
- 考虑依赖的许可证和安全影响
- 制定依赖更新和维护策略

### 错误处理
- 定义统一的错误处理策略
- 设计适当的日志记录机制
- 规划监控和告警系统
- 考虑灾难恢复和数据备份

### 性能优化
- 识别潜在的性能瓶颈
- 设计性能监控和分析机制
- 制定优化策略和基准
- 考虑负载均衡和缓存策略

### 安全考虑
- 识别安全风险和威胁模型
- 定义身份验证和授权策略
- 规划数据加密和保护措施
- 包含安全测试和审计要求

### 文档要求
- 记录所有技术决策的理由
- 包含架构图和流程图
- 提供 API 文档和示例
- 包含运维和部署文档

### 团队协作
- 定义团队角色和职责
- 制定沟通和协作流程
- 规划代码审查和知识分享
- 考虑团队技能发展和培训需求


## 概述

用户在触发消息中 `/speckit.tasks` 后输入的文本**就是**任务描述. 假设你始终可以在本次对话中访问它, 即使下面字面上显示 `$ARGUMENTS`. 除非用户提供了空命令, 否则不要要求用户重复.

基于该实施计划, 执行以下操作:

1. **加载实施计划**
   - 从 `specs/[feature]/plan.md` 加载实施计划
   - 确认计划已通过完整性验证

2. **分析功能需求**
   - 识别所有功能需求
   - 理解需求之间的依赖关系
   - 识别非功能需求（性能、安全、可用性等）

3. **分解任务**
   - 将实施计划分解为具体的开发任务
   - 为每个任务分配优先级（P1-必须、P2-重要、P3-可选）
   - 估计每个任务的工作量（人天）
   - 识别任务间的依赖关系

4. **创建任务清单**
   - 按优先级和依赖关系组织任务
   - 为每个任务提供清晰的描述
   - 定义任务的验收标准
   - 指定负责的角色或团队

5. **生成任务文件**
   - 使用模板结构将任务清单写入 `specs/[feature]/tasks.md`
   - 用从实施计划派生的具体细节替换占位符
   - 保持章节顺序和标题
   - 包含任务分配和时间估算

6. **验证任务完整性**
   - 检查任务清单是否覆盖所有功能需求
   - 验证任务分解的合理性
   - 确认优先级和依赖关系正确
   - 评估总体时间估算的可行性

7. **报告完成情况**
   - 包括任务文件路径
   - 总结任务分解的主要特点
   - 列出下一阶段（`/speckit.implement`）的准备就绪状态

## 通用指南

### 任务分解原则
- **原子性**: 每个任务应该是最小的可执行单元
- **独立性**: 任务应该尽可能独立，减少相互依赖
- **可测试性**: 每个任务都应该有明确的验收标准
- **可追踪性**: 任务应该能够追踪到具体的需求

### 优先级定义
- **P1 (必须)**: 核心功能，项目成功的关键
- **P2 (重要)**: 重要功能，影响用户体验但不是必需的
- **P3 (可选)**: 增强功能，提升体验但不影响核心功能

### 任务描述要求
- 使用清晰、具体的语言
- 包含任务的目标和预期结果
- 明确说明任务的输入和输出
- 指定相关的技术栈或工具

### 验收标准编写
- 使用可验证的、客观的标准
- 包含功能性和非功能性要求
- 明确说明测试方法
- 确保标准是可量化的

### 时间估算方法
- 基于历史数据和经验
- 考虑任务的复杂度和风险
- 包含缓冲时间以应对不确定性
- 定期回顾和调整估算

### 依赖关系管理
- 识别硬依赖（必须完成的任务）
- 识别软依赖（建议完成的任务）
- 考虑外部依赖（第三方服务、团队等）
- 制定依赖风险缓解策略

## 附加要求

### 任务跟踪
- 为每个任务分配唯一标识符
- 定义任务状态（待办、进行中、已完成等）
- 建立任务进度跟踪机制
- 定期更新任务状态和进度

### 质量保证
- 在任务中包含代码审查要求
- 定义测试覆盖率目标
- 包含文档编写任务
- 考虑性能和安全测试

### 风险管理
- 识别高风险任务
- 制定风险缓解策略
- 建立风险监控机制
- 准备应急计划

### 团队协作
- 考虑团队成员的技能和经验
- 合理分配任务以平衡工作负载
- 建立知识共享机制
- 定期进行团队同步

### 持续改进
- 收集团队对任务分解的反馈
- 定期回顾任务完成情况
- 识别改进机会
- 调整任务分解方法

## 任务模板

每个任务应该包含以下信息：

```markdown
### 任务 [ID]: [任务标题]

**优先级**: P1/P2/P3
**估算时间**: [X] 人天
**依赖**: [任务 ID 或 "无"]

**描述**:
[任务的详细描述，包括目标和预期结果]

**验收标准**:
- [ ] [具体、可验证的标准 1]
- [ ] [具体、可验证的标准 2]
- [ ] [具体、可验证的标准 3]

**相关需求**:
- [需求 ID 或链接]

**负责角色**:
[指定负责的角色或团队]

**备注**:
[其他相关信息或说明]
```

确保所有任务都遵循这个模板，以保持一致性和可读性。
